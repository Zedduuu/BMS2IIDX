## 2026-11-06：「统计 NPS 报错」修了半小时

### 事实经过

| 时间 | 我做了什么 | 结果 |
|---|---|---|
| 18:30 | 上一轮为了给「谱面作者」列补数据，写了个**全量迁移**：把索引里 10.4 万条记录重新读一遍文件头 | 单线程约 40 分钟，超时设 30 分钟，**整段静默卡死**，被中断 |
| 18:45 | 用户说「统计 nps 报错了」。我没有拿到异常文本，凭代码猜：线程对象重名（`self.worker`） | 真实存在，但不是这次的原因 |
| 18:47 | 又猜：SQLite 读到旧快照 → 改成"完成后新开连接读一次" | 也不是原因 |
| 18:50 | 又猜：`on_select` 把刚填的数字覆盖成 `—` → 删掉那次刷新 | 症状变了，仍不是原因 |
| 18:54 | 在 `_on_stats_done` 外面包一层日志，打印 `res` 与 `_stats_song` | **一秒钟看到真凶**：`AttributeError: 'BmsLibraryPage' object has no attribute '_reselect_folder'` |
| 18:56 | 补回被删掉的方法 | 修好 |

### 根因

上一轮我改 `run_stats` 时用了「切片替换」：

```python
t = t[:start] + new + t[end:]      # start..end 之间的东西全没了
```

`_reselect_folder()` 正好夹在 `run_stats` 和 `_on_stats_progress` 中间，被整段删掉。
而我只跑了 `ast.parse()`（**只查语法**），语法当然是对的；方法不存在要到运行时才炸。

### 为什么拖了半小时（六条，都是我的问题）

1. **没拿异常文本就开始改**。用户只说"报错了"，正确的第一反应是"把报错那行贴我"或自己复现，而不是猜。
2. **先猜后验**。线程重名、DB 快照都是"看起来很像"的原因，改完发现不是，又接着猜下一个——每次都全量改代码 + 重启测试。
3. **大块替换没有结构校验**。`ast.parse` 通过 ≠ 代码完整；缺方法、缺属性它查不出来。
4. **测试脚本自己会卡**。GUI 测试里放了 `QTimer` 长等待 + 真实弹窗，两次卡到工具超时，白等 20 分钟。
5. **测试状态被污染**。反复对同一首歌跑统计，数据已经写进索引，于是走到"已经统计过了"分支，掩盖了真正的报错路径，让结论看起来自相矛盾（"有时好有时坏"）。
6. **优先级反了**。用户说"报错了"，我却先去调左右分栏、列宽、按钮文案，把"修错"排在"好看"后面。

### 规则（写进提交前自查）

**R0 报错先查日志，再问人**

用户说"报错了"时的正确顺序：

1. 打开 `library/logs/app-YYYYMMDD.log`（帮助页有「打开日志文件」按钮），
   从下往上找 `✗` / `Traceback` / `[stderr]`
2. 日志里没有 → **直接问用户要报错原文**（弹窗文字 / 截图 / 日志最后 50 行）
3. 两者都没有 → 自己最小复现（同一个操作、同一份数据）
4. 拿到 `异常类型 + 消息 + 行号` 之后才允许改代码

> 这条是在被批评之后补的：当时用户只说"统计 nps 报错了"，我没查日志也没问，
> 直接猜了三个原因，各改一遍。而其实程序里早就有 excepthook，
> 只是**日志没落盘**——所以这一版把日志写进 `library/logs/app-*.log`，
> 并给帮助页加了「打开日志文件/文件夹」两个按钮。


**R1 报错先取证**
拿到 `异常类型 + 消息 + 位置` 再动手。拿不到就自己最小复现；**不许凭"看起来像"直接改代码**。
GUI 里统一用 `_on_xxx_failed` 弹窗带上 `type(e).__name__` 和堆栈最后一行。

**R2 大块替换后跑结构自查**
任何 `t[:a] + new + t[b:]` 之后，必须跑：

```powershell
python tools\check_self_calls.py     # 查"用了但类上没有"的 self.xxx
python -c "import gui.ui"            # 真正导入一次
```

`check_self_calls.py` 已经抓出另一个潜藏 bug：`do_deploy()` 引用了不存在的 `btnDeploy`
（旧转换页遗留的死代码），真被调用就会崩。

**R3 GUI 测试脚本必须能自己结束**
- 不用真实弹窗：一开始就把 `QMessageBox.question/information/warning` 替换成 lambda
- 不用长 `QTimer`：整条链路 ≤ 6 秒；脚本外层再加工具超时
- 结果写文件（`work/xxx.txt`），别指望 stdout（它被重定向进日志面板）

**R4 测试要幂等**
测「统计」前先 `UPDATE charts SET stats_at=NULL ... WHERE folder='...'`，
每次都从"未统计"状态开始；否则会走进"已统计"分支，测了个寂寞。

**R5 超过 2 分钟的操作不许静默等待**
先跑 50 条小样本 → 实测单条耗时 → 估算总量 → 再决定。
全库级操作（10 万文件）必须做成**后台任务 + 进度**，不许用一次调用等 30 分钟。

**R6 一个回合只做一件事**
先修用户报的错，再做外观。混在一起时，新引入的 bug 会被误当成旧 bug 在排查。

### 提交前自查（30 秒）

```powershell
python -m compileall -q core gui tools
python tools\check_self_calls.py
python -c "import gui.ui; import gui.services; import core.convert"
```

三条都过，再提交。

## 2026-11-06 之前的几条

- **`trash_song` 崩溃**：先写 `record.bin` 再 `mkdir`，歌没有资源文件时 `FileNotFoundError`。
  → 规则：**先建目录再写文件**，删除类操作一律"先备份/入回收区，再改记录"。
- **多选「彻底删除文件（保留记录）」把记录也删了**：`remove_song` 里无条件调了
  `reapply.remove_song`，没看 `drop_library` 参数。→ 规则：**参数即契约，写分支时必须逐个覆盖测试**。
- **把「没重启游戏」的测试当成结论**：wmv 覆盖失败被误判为"layeredfs 不能覆盖"。
  → 规则：**测试前确认环境状态**（进程是否重启、文件何时放入），并在结论里写明。
- **全量迁移卡死**（本次 18:30 那次）：见 R5。
